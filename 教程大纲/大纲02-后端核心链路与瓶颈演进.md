## 能力模块 1：多租户存储、业务本体建模与线上安全变更的瓶颈演进

### 第 1 节：多租户隔离演进 —— 从“混住一表”到“Schema 隔离 + 共享主从连接池”
- **对应主线**：第 1 站（销售录入新线索，平台怎么确保 A 公司和 B 公司绝不串数据，同时又不把数据库打爆？）
- **瓶颈演进逻辑链**：
  - *V1 直觉写法*：所有客户共用一张表加 `tenant_id` → **瓶颈**：只要任何一条 SQL 漏写过滤条件就酿成跨租户泄露事故。
  - *V2 粗暴升级*：给每家公司单独建一个物理数据库实例 → **瓶颈**：入驻 3,000 家公司就要维护几千个连接池，数据库连接直接炸穿。
  - *Twenty 工业演进*：同库下按租户切分 PostgreSQL **Schema**（一户一间精装独立单元）+ 全局共享主从物理连接池 + 请求链路 `AsyncLocalStorage` 自动绑定当前租户身份与表结构缓存（涉及 `twenty-orm`、`workspace-datasource`）。
- **2026 面试三层追问（锚定 `B06` `B07` `A10`）**：
  - *L1*：多租户隔离为什么选 Schema 隔离而不选共享表行级字段或独立物理库？
  - *L2*：多个租户共享同一个数据库连接池，并发请求时怎么保证前一个人的 Schema 上下文不会串到下一个人身上？
  - *L3*：如果公司数膨胀到十万级，单库几万个 Schema 会暴露什么新瓶颈？下一步怎么演进拆分？

### 第 2 节：业务本体与权限建模演进 —— 为什么绝不让业务与 AI 直接碰数据库裸表？
- **对应主线**：第 1 站（客户想自己加一个“线索意向评分”字段，怎么不动核心代码就能生效并控好权限？）
- **瓶颈演进逻辑链**：
  - *V1 直觉写法*：把字段写死在表里，或者开放 SQL 接口/表名直连 → **瓶颈**：每家企业要定制字段就得改代码发版；更致命的是，如果以后接入 AI，模型对着缩写字段和多张关联表直写 SQL，根本看不懂“已成交的线索不能随便回退”这类业务不变量。
  - *Twenty 工业演进*：构建元数据驱动的 **动态对象与字段模型**（`object-metadata`、`field-metadata`）+ 统一 **RBAC 与行级权限网关**（`permissions`）+ 对外只暴露带有业务语义和校验边界的实体动作。
- **2026 面试三层追问（锚定 `B03` 字节三面、`A10`）**：
  - *L1*：为什么业务概念（Action/对象模型）不能直接一一映射数据库底表？
  - *L2*：业务动作（Action）粒度怎么划分？太细和太粗分别会炸出什么问题？
  - *L3*：对比“先花大力气做领域本体建模”与“用 CLI + Skill 快速封装老接口”两种路线，如果面对难以改造的存量老系统怎么折中？

### 第 3 节：查询性能演进 —— 消除 N+1、索引失效与数据库底层对比（PG vs MySQL）
- **对应主线**：第 1 站（列表一次展示 50 条线索和对应公司、负责人信息，怎么做到 1 次查完而不变成 101 次查询？）
- **瓶颈演进逻辑链**：
  - *V1 直觉写法*：先查出 50 条线索，再用 `for` 循环逐条去查所属公司 → **瓶颈**：经典 **N+1 查询**把连接池打满；或者关联时隐式类型转换/套 `CAST` 函数导致索引全部失效。
  - *Twenty 工业演进*：自定义查询执行引擎配合 `dataloaders` 批量合并请求 + 元数据级索引定义（`index-metadata`）+ **高频跨库地基补齐**（说清为何磁盘索引普遍选 B+ 树省寻页 IO，而纯内存结构里红黑树/跳表未必比 B+ 树慢；并帮只学过 MySQL 的面试者对齐 PostgreSQL 与 MySQL InnoDB 在 MVCC 快照读和主从复制上的异同）。
- **2026 面试三层追问（锚定 `B01` `B05` `B07` `B09`）**：
  - *L1*：什么是 N+1 问题、怎么优化？除了加 `CAST`，还有哪些常见动作会让联合索引突然失效？
  - *L2*：反常识陷阱题——“二叉树一定比 B+ 树查询慢吗？”（切到纯内存前提拆穿）。
  - *L3*：从页面变慢到抓出一条慢 SQL，你的标准排查顺序是什么？（结合 `EXPLAIN` 与项目使用 PG 的事实边界作答，不编造 MySQL 线上数字）。

### 第 4 节：线上改表安全演进 —— 租户随时增删字段，如何做到不锁死线上业务？
- **对应主线**：第 2 站（管理员在白天的业务高峰期给线索表新增一个自定义字段或索引，为什么不会让全公司销售的查询全卡死？）
- **瓶颈演进逻辑链**：
  - *V1 直觉写法*：直接下发 DDL `ALTER TABLE` 改表 → **瓶颈**：如果此时刚好有一个长慢查询没跑完，DDL 会排在后面抢元数据锁，进而把**之后所有正常读写请求全部堵死排队**导致雪崩；改到一半报错还会留下半残废表结构。
  - *Twenty 工业演进*：打造 **声明式安全迁移引擎**（`workspace-manager`）——先对比新旧元数据算出最小变更动作、强设 **8 秒锁超时**（抢不到锁宁可失败也不堵业务）、自动查询数据库当前阻塞进程辅助排障，并且每步 DDL 生成配对的**逆向回滚动作**保证失败复原。
- **2026 面试三层追问（锚定 `B07` 系统扩展性边界、`B06`）**：
  - *L1*：为什么一个看起来很简单的“加字段”操作有可能把整个系统查询全卡死？
  - *L2*：改表到一半因超时中断了，Twenty 的声明式引擎是怎么保证原子性和可回滚的？
  - *L3*：除了设锁超时，面向千万级大表必须加字段或建索引时，工程上还有哪些无锁/低感知变更方案？

## 能力模块 2：高并发缓存一致性、异步队列容错与线上排障的瓶颈演进

### 第 5 节：缓存架构演进 —— 从“直打数据库”到“多级缓存 + 单飞 + Lua 原子校验”
- **对应主线**：第 2 站（每个接口都要读取租户的元数据定义和权限规则，怎么防止成千上万并发把数据库读穿？）
- **瓶颈演进逻辑链**：
  - *V1 直觉写法*：每次进接口现查 PG → **瓶颈**：高频结构读取撑爆数据库；简单套一层 Redis 后又遇到**热点失效瞬间几百个请求同时冲去查库（缓存击穿）**、**序列化超大对象变成大 Key 卡死单线程 Redis**、以及**版本发布切换时新 Key 全空引发集体回源**。
  - *Twenty 工业演进*：`workspace-cache` + `cache-storage` + `cache-lock` 组合拳——进程内超短 TTL 本地缓存兜顶 + Redis Hash 存储 + **Singleflight（单飞）并发回源合并**（同一个 Key 只放 1 个代表去查库，其余等着分结果）+ **Lua 脚本原子比较替换（CAS）**与空闲清理；补充高频考察的 Key 版本号灰度切流、TTL 评估与热 Key 打散。
- **2026 面试三层追问（锚定 `B01` `B04` `B08` `B09`）**：
  - *L1*：为什么标准 Cache Aside 是“先写库、再删缓存”，而不是顺便直接更新缓存？
  - *L2*：灵魂深挖（`B09`）——“既然写法是对的，为什么线上还会出现长达 3 分钟甚至 10 分钟的数据不一致？”（5 大真实根因全拆）。
  - *L3*：如果业务明确要求“用户刚修改完权限/价格，刷新页面绝对必须读到最新值”，在最终一致之外怎么兜底？

### 第 6 节：事务与副作用一致性演进 —— 为什么绝不能在事务里直接发消息或删缓存？
- **对应主线**：第 2 站（线索入库事务还没真正提交，如果提前发出 MQ 事件或提前删了缓存会怎样？）
- **瓶颈演进逻辑链**：
  - *V1 直觉写法*：在一个 Service 函数里先 `save(lead)`、顺手就 `deleteCache()` + `pushQueue()`，最后事务结束统一 `commit` → **瓶颈**：如果后面突然抛错导致事务回滚，消息已经发出去了、别人已经读到旧数据回填进缓存了，彻底失真。
  - *Twenty 工业演进*：引入 **事务后延迟副作用机制（`afterCommit` 钩子）**——在事务块里先把“提交后要删哪些缓存、发哪些事件”暂存进请求上下文清单，**只有确认数据库 `COMMIT` 成功那一刹那才统一触发**；并与传统大厂的 **本地消息表 + 定时任务扫表兜底** 做架构对比。
- **2026 面试三层追问（锚定 `B04` `B06`）**：
  - *L1*：事务确实提交成功了，但恰好在执行 `afterCommit` 删缓存或发消息前一毫秒进程断电崩溃，怎么补偿？
  - *L2*：如果用“本地消息表”或“消费端 Redis `SETNX` 占位”防重，消费处理中途异常崩了导致占位键一直残留卡死怎么办？
  - *L3*：写库和发消息跨了两个系统，到底存不存在“端到端恰好一次（Exactly-Once）”？工程上真正靠什么落地？

### 第 7 节：异步队列与长任务演进 —— 从“12 秒接口卡死”到“限流队列 + 分段让渡”
- **对应主线**：第 3 站（销售一次性导入几千条企业线索，并触发多步骤自动跟进，怎么既秒级响应又不让一个大户把全平台队列堵死？）
- **瓶颈演进逻辑链**：
  - *V1 直觉写法*：同步接口里直接读文件逐条写库调外部服务 → **瓶颈**：接口动辄十几秒超时；改成普通消息队列后，某一家大客户突然批量塞进 5 万条任务，所有正常小客户被堵在后面干等；或者一个复杂工作流一口气跑上百步把 Worker 死死占住。
  - *Twenty 工业演进*：`message-queue`（基于 Redis + BullMQ）配置 **工作区分组速率限制器** 与 **Worker 内存水位守护** + `workflow` 引擎 **每执行 20 步主动让出一次控制权** 挂起回队列；同时横向补齐后端高发专题：**Kafka 单分区单消费者与位点（Offset）提前提交惨案**、**分布式锁细粒度（用户+文件 SHA-256 指纹）与数据库唯一索引最终防线**、以及 **不用 MQ 时如何仅靠数据库 `FOR UPDATE SKIP LOCKED` 搭可靠异步状态机**。
- **2026 面试三层追问（锚定 `B05` `B08` `B10` `A03`）**：
  - *L1*：为什么 Twenty 用 Redis + BullMQ 而没有硬上 Kafka？两个中间件都能做异步时你按什么逻辑取舍？
  - *L2*：经典位点陷阱——5 个消费者拿到 1~5 号消息，5 号最先做完提交位点 `5`，1~4 号全挂了，怎么找回 1~4 号？
  - *L3*：不用 MQ 只用数据库设计一套异步系统该怎么防并发抢重？它的数据量天花板在哪？

### 第 8 节：后端压轴生存课 —— 下游超时回查与「接口 200ms 飙到 5s + CPU 暴涨」排障演练
- **对应主线**：第 3 站（异步调用第三方企查查或内部建单超时，或者线上某个接口忽然卡死且 CPU 拉满，如何保命定位？）
- **核心逻辑链**：
  - **超时 ≠ 没成功**：调写接口超时后严禁盲目重试！标准动作是“先带业务唯一幂等键 → 超时凭原键回查结果 → 无回查能力则挂起为状态未知待人工/对账”。
  - **200ms→5s + CPU 飙升四步救急顺序**：① 定影响面与变更时间对齐 → ② 拆分段耗时（判断是本机 CPU 死算还是傻等下游引起重试放大） → ③ CPU 高盯火焰图/线程栈/GC，CPU 低盯慢 SQL/连接池/缓存击穿 → ④ 先限流/降级/回滚止血，再彻底修根因。
- **2026 面试三层追问（锚定 `B02` `B04` `B10`）**：
  - *L1*：批量同时查 5 个下游，有 1 个超时了接口应该怎么返回？别忘了怎么处理那个卡住的下游连接？
  - *L2*：接口耗时从 200ms 变 5s 且 CPU 飙升，一上来就说是慢 SQL 为什么会被面试官直接扣分？
  - *L3*：如果优化后你没有亲手跑过线上真实压测，被问“你优化完 P99 降了多少”时怎么诚实作答不露馅？（锚定 `seed-be-10` 口径红线）。
